# Day 16 - DNS Queries, Messages, and Record Types

## 1. DNS Queries and Responses

When an endpoint needs to find a network resource, it doesn't just send a random message - it formats a structured **DNS query**. 

In practical terms, a DNS query asks a specific question: 
> *"What is the IPv4 address associated with `example.com`?"*

The recursive or authoritative server receives this query, processes it, and replies with a **DNS response**. Depending on what it finds, that response might contain:
* The requested address record (an answer).
* A referral pointing to another nameserver (like a TLD or authoritative server).
* An error code indicating the domain doesn't exist.
* Supplementary or additional records.

## 2. Anatomy of a DNS Message Structure

If you capture traffic using Wireshark and expand a DNS packet, you'll notice that DNS messages follow a rigid layout. Understanding these header fields is critical when you are triaging suspicious network behavior.

### 2.1 Core Header Fields

| Header Field | What It Is | Why It Matters to a SOC Analyst |
| :--- | :--- | :--- |
| **Transaction ID (TXID)** | A 16-bit random number generated by the client to pair requests with incoming responses. | Essential for spotting DNS spoofing or cache poisoning attempts. If an attacker wants to inject fake responses, they have to guess this random ID. |
| **QR (Query/Response)** | A 1-bit flag (`0` for query, `1` for response). | Allows you to quickly filter packets in Wireshark to separate outbound requests from incoming server replies. |
| **RD (Recursion Desired)** | Set to `1` by the client telling the resolver: *"Please do the full lookup if you don't have this cached."* | Standard behavior for normal enterprise endpoints querying their local DNS server. |
| **RA (Recursion Available)** | Set to `1` by the server in its response to confirm: *"Yes, I support recursive lookups."* | Helps verify if a target nameserver is configured as an open public resolver. |
| **AA (Authoritative Answer)** | Set to `1` if the responding server is the direct owner/source of truth for that zone. | Tells you whether the answer came directly from the authoritative nameserver or a cached intermediary. |
| **TC (Truncation)** | Indicates that the message exceeded 512 bytes over UDP and was truncated. | **High security relevance:** Forces a fallback to TCP port 53. Attackers sometimes abuse large payloads, making TC flags valuable in anomaly hunting. |
| **RCODE (Response Code)** | Status indicator returned by the server (`0` for NoError, `3` for NXDOMAIN). | **Crucial for threat detection:** A high volume of `NXDOMAIN` (non-existent domain) responses from a single host often indicates malware running a Domain Generation Algorithm (DGA). |

## 3. Deep Dive into Essential DNS Record Types

As a security analyst, you need to know that DNS does much more than just translate website names into IP addresses. It maintains various record types, each serving a unique function—and each carrying specific security risks.

### 3.1 The Core Record Types

* **`A` (Address Record):** 
  * *Purpose:* Maps a human-readable domain name to a 32-bit IPv4 address (e.g., `example.com` $\rightarrow$ `93.184.216.34`).
  * *Security Context:* Tracked during investigations to identify malicious hosting infrastructure or rapid IP changes (Fast Flux).

* **`AAAA` (IPv6 Address Record):**
  * *Purpose:* Maps a domain name to a 128-bit IPv6 address.
  * *Security Context:* Increasingly monitored because malware authors sometimes use IPv6 tunnels to bypass traditional IPv4 firewall monitoring.

* **`CNAME` (Canonical Name Record):**
  * *Purpose:* Acts as an alias, pointing one domain name to another (e.g., `www.example.com` $\rightarrow$ `example.com`).
  * *Security Context:* Vulnerable to **Subdomain Takeover** if an organization abandons a cloud resource (like an AWS S3 bucket) while leaving the dangling CNAME DNS record active.

* **`MX` (Mail Exchange Record):**
  * *Purpose:* Identifies the mail servers responsible for handling email for a domain, complete with priority values (lower numbers = higher priority).
  * *Security Context:* Inspected during phishing investigations to check if an organization's email routing has been tampered with.

* **`NS` (Name Server Record):**
  * *Purpose:* Designates the authoritative nameservers responsible for a DNS zone.
  * *Security Context:* Checked during DNS hijacking investigations to ensure attackers haven't swapped out legitimate nameservers for malicious ones.

* **`SOA` (Start of Authority):**
  * *Purpose:* Contains administrative metadata about a zone, including the primary nameserver, contact email, serial numbers, and refresh timers.

* **`TXT` (Text Record):**
  * *Purpose:* Stores arbitrary text strings; widely used for domain ownership verification (SPF, DKIM, DMARC) and security policies.
  * *Security Context:* **The primary vector for DNS Tunneling.** Attackers often encode binary data or commands inside long subdomains of TXT queries to smuggle data past firewalls.

* **`PTR` (Pointer Record):**
  * *Purpose:* Enables reverse DNS lookups, mapping an IP address back to a hostname.
  * *Security Context:* Used by mail servers and SOC analysts to verify if an incoming connection has a valid reverse mapping.

* **`SRV` (Service Record):**
  * *Purpose:* Specifies hostname and port information for specific network services (like Active Directory domain controllers).

* **`CAA` (Certificate Authority Authorization):**
  * *Purpose:* Specifies which Certificate Authorities (CAs) are permitted to issue SSL/TLS certificates for a domain, preventing unauthorized certificate generation.
