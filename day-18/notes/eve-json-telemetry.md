# Technical Note: Suricata EVE JSON Telemetry & SIEM Integration

**Author:** Serah Mulwa

**Module:** Day 18 - Network Security Monitoring & Intrusion Detection

---

## 1. Executive Summary

In a modern Security Operations Center (SOC), unformatted or unstructured log files hinder effective threat hunting. Legacy security engines wrote flat text logs (such as `fast.log`), which required brittle regular expressions (regex) to parse and ingest into Security Information and Event Management (SIEM) systems.

Suricata solves this through **EVE (Extensible Event Format)** JSON logging. Every network observation—including rule alerts, DNS queries, HTTP headers, TLS handshakes, file extractions, and session flow closures—is recorded as a structured, machine-parseable JSON object.

This technical guide documents the structure, schema, and field-level breakdown of Suricata's `eve.json` telemetry, demonstrating command-line parsing techniques using `jq` and detailing how structured network telemetry integrates into enterprise SIEM pipelines.

---

## 2. The Role of EVE JSON in the SOC Pipeline

Structured telemetry serves as the primary bridge connecting raw network packet collection with centralized security monitoring platforms.

```
       RAW NETWORK TRAFFIC / PCAP
                   │
                   ▼
        [ Suricata NIDS Engine ]
                   │
                   ▼
      [ Structured EVE JSON Stream ]
       (/var/log/suricata/eve.json)
                   │
                   ▼
  ┌────────────────┴────────────────┐
  ▼                                 ▼
[ Terminal CLI Triage ]     [ SIEM Ingestion Engine ]
(Python, jq, grep)          (Elasticsearch, Splunk, Wazuh)
  │                                 │
  └────────────────┬────────────────┘
                   │
                   ▼
     [ SOC Analyst Investigation ]
```

### Key Advantages of EVE JSON over Unstructured Logging:
* **Machine Parseability:** Every event uses consistent key-value pairs (`"key": "value"`), eliminating regex dependencies during log ingestion.
* **Unified Event Types:** A single log engine captures multiple protocol layers (Layer 3/4 flow state alongside Layer 7 application metadata) in unified records.
* **Cross-Event Correlation:** Through the `flow_id` key, separate protocol logs (e.g., a DNS lookup followed by a TCP alert) can be linked back to the exact same communication session.

## 3. Deconstructing a Suricata EVE JSON Alert Event

Below is a representative EVE JSON alert record generated by Suricata during a network security scan:

```json
{
  "timestamp": "2026-11-04T21:15:30.123456+0300",
  "flow_id": 847291049281,
  "in_iface": "eth0",
  "event_type": "alert",
  "src_ip": "192.168.1.50",
  "src_port": 54321,
  "dest_ip": "198.51.100.25",
  "dest_port": 443,
  "proto": "TCP",
  "app_proto": "tls",
  "alert": {
    "action": "allowed",
    "gid": 1,
    "signature_id": 2024001,
    "rev": 2,
    "signature": "LOCAL LAB Suspicious TLS Handshake Detected",
    "category": "Potentially Bad Traffic",
    "severity": 2
  },
  "pcap_cnt": 142
}
```

### Essential Field Schema Reference:

| Field Name | Data Type | Description & Security Significance |
| :--- | :--- | :--- |
| `timestamp` | String (ISO 8601) | Precise time (with UTC offset) when the event occurred; essential for multi-source timeline reconstruction. |
| `flow_id` | Integer | Unique identifier assigned to the bi-directional communication stream; connects alerts to protocol metadata. |
| `event_type` | String | Specifies the log type (`alert`, `dns`, `http`, `tls`, `flow`, `fileinfo`). |
| `src_ip` | String | Source IP address initiating the connection or packet stream. |
| `src_port` | Integer | Source ephemeral port number. |
| `dest_ip` | String | Target destination IP address receiving the connection. |
| `dest_port` | Integer | Destination service port (e.g., `80`, `443`, `53`, `3389`). |
| `proto` | String | Layer 4 transport protocol (`TCP`, `UDP`, `ICMP`). |
| `app_proto` | String | Application protocol identified by Suricata's Deep Packet Inspection (DPI) engine (`dns`, `http`, `tls`). |
| `alert.signature_id` | Integer | Unique rule identifier (SID) that triggered the alert. |
| `alert.signature` | String | Human-readable alert description configured in the rule file. |
| `alert.severity` | Integer | Priority classification (1 = High, 2 = Medium, 3 = Low/Informational). |
| `pcap_cnt` | Integer | Packet sequence number within an offline `.pcap` capture; used to jump directly to the exact frame in Wireshark. |

## 4. Terminal Command-Line Triage Techniques (`jq`)

Security analysts frequently inspect `eve.json` directly from Linux terminal environments using `jq`, a lightweight command-line JSON processor.

### 4.1 Filter and Format All Triggered Alerts
To filter out noise and view formatted alert messages with timestamps and IP addresses:
```bash
jq 'select(.event_type=="alert") | {time: .timestamp, src: .src_ip, dest: .dest_ip, signature: .alert.signature}' /var/log/suricata/eve.json
```

### 4.2 Extract Unique DNS Queries
To extract all domain names queried across the network capture:
```bash
jq 'select(.event_type=="dns") | {query: .dns.rrname, type: .dns.rrtype, client: .src_ip}' /var/log/suricata/eve.json
```

### 4.3 Aggregate Top Triggered Alert Signatures
To count and rank the most frequent alert rules triggered in a capture:
```bash
jq -r 'select(.event_type=="alert") | .alert.signature' /var/log/suricata/eve.json | sort | uniq -c | sort -nr
```

## 5. SIEM Ingestion & Incident Investigation Workflow

When integrated into enterprise SIEM solutions (e.g., Elastic Stack/Elastic Agent, Splunk Universal Forwarder, or Wazuh Manager):

1. **Log Collection:** A lightweight shipper monitors `/var/log/suricata/eve.json` and forwards new entries in real time.
2. **Field Indexing:** The SIEM maps JSON key paths (such as `src_ip` to `source.ip`) according to standard taxonomies like Elastic Common Schema (ECS).
3. **Correlation & Dashboarding:** Analysts query aggregated events, build visualizations (e.g., spikes in DNS query volume), and configure correlation rules combining host alerts with Suricata network events.

---

## 6. Key Takeaways for Analysts

1. **`eve.json` is the Gold Standard:** Unstructured text logs are obsolete in scalable SOC environments; structured JSON enables rapid querying and automated triage.
2. **Leverage `flow_id`:** When an alert triggers, copy its `flow_id` and query `eve.json` for all records sharing that ID to see the full session context (HTTP requests, DNS lookups, TLS parameters).
3. **Use `pcap_cnt` for PCAP Forensics:** During offline PCAP analysis, use the `pcap_cnt` integer to jump straight to the exact packet frame in Wireshark without manually scanning thousands of packets.
