# Technical Note: Defining the Investigation Hypothesis & Validation Framework

**Author:** Serah Mulwa

**Module:** Day 20 - Integrated Network Threat Hunting & Detection Engineering

## 1. Executive Summary

Professional threat hunting is never an aimless exercise in browsing log files. It begins with a structured, testable assumption about what network telemetry should look like under specific conditions. By defining a clear hypothesis, security analysts turn command-line log analysis into a rigorous scientific process.

This technical note documents the formal investigation hypothesis for our Day 20 practical lab. It establishes the criteria required to prove or disprove the hypothesis and outlines how to troubleshoot telemetry discrepancies between Suricata and Zeek.

## 2. The Day 20 Investigation Hypothesis

For our integrated lab exercise, our official testable hypothesis is:

> *"A DNS request generated by our authorized virtual machine and matching our local Suricata rule should be visible in the corresponding Zeek connection and DNS records. Furthermore, both independent tools should successfully correlate the matching network flow through a shared Community ID hash."*

## 3. Supporting vs. Contradicting Evidence

When evaluating telemetry outputs, an analyst must know precisely what evidence confirms the hypothesis and what indicates a configuration fault or visibility gap.

### What Evidence Supports the Hypothesis?
* **Packet Capture Integrity:** The raw `.pcap` file contains the actual DNS query packets.
* **Suricata Alert Generation:** Suricata reads the PCAP, evaluates its signature rules, and successfully triggers the expected local alert.
* **Community ID (Suricata):** The Suricata EVE JSON alert record contains a valid `community_id` string (e.g., `1:LQU9...`).
* **Zeek Processing:** Zeek reads the same PCAP and processes connection and DNS states without error.
* **Community ID (Zeek):** Zeek’s `conn.log` contains an identical `community_id` matching the Suricata alert.
* **Protocol Association:** Zeek's `dns.log` contains the corresponding DNS query record, tied to the connection via a shared session `uid`.
* **Temporal Consistency:** Timestamps across Suricata and Zeek logs align within milliseconds, and endpoint 5-tuples match perfectly.

### What Evidence Contradicts the Hypothesis?
* **Orphaned Alerts:** A PCAP contains the expected request and generates a Suricata alert, but Zeek produces zero corresponding records in `conn.log`.
* **Hash Mismatches:** Suricata and Zeek generate different `community_id` strings despite processing the exact same packet stream.
* **Timeline Drift:** Timestamps or endpoint tuples differ significantly, suggesting the logs describe separate flows.
* **Sensor Faults:** One of the tools fails to initialize or output records due to a missing configuration parameter or seed mismatch.

## 4. Troubleshooting Correlation Failures

A failed correlation does not automatically mean a security tool is broken. When discrepancies occur, professional analysts investigate systematically:
1. **Seed Configuration:** Were Suricata and Zeek initialized with matching seeds (e.g., `seed: 0`)?
2. **Packet Loss / Drop:** Did the capture interface drop packets (`missed_bytes` in Zeek's stats) due to high CPU load?
3. **Flow Visibility:** Did the capture window begin *after* the connection handshake occurred, missing essential state transitions?
4. **Rule Syntax Mismatch:** Did the DNS query string fail to match the exact regular expression or syntax defined in the Suricata rule?

## 5. Key Portfolio Takeaways

* Hypothesis-driven testing transforms log analysis from guesswork into a structured scientific methodology.

* Mismatches between independent security tools serve as critical clues for diagnosing configuration errors or packet loss.

* Documenting your investigative assumptions and troubleshooting steps demonstrates elite operational maturity to hiring managers.
