# Technical Note: Zeek DNS Protocol Analysis & dns.log Mechanics

**Author:** Serah Mulwa

**Module:** Day 19 - Network Threat Hunting with Zeek

## 1. Executive Summary

Over $90\%$ of malicious software campaigns rely on the **Domain Name System (DNS)** at some stage during an intrusion—whether to resolve dynamic Command and Control (C2) infrastructure, execute automated Domain Generation Algorithms (DGAs), or exfiltrate stolen credentials via covert DNS tunneling.

While connection-level logging (`conn.log`) captures transport socket pairs (e.g., `10.0.2.15:52344 -> 192.168.100.1:53`), **`dns.log`** provides critical application-layer visibility into requested domain strings, record query types, resolver response codes, and returned IP mappings. This technical note details `dns.log` field architecture, DNS-based threat hunting methodologies, and SOC triage workflows.

## 2. Anatomy of a Zeek DNS Record

Below is an example of a JSON-formatted DNS log record generated by Zeek:

```json
{
  "ts": 1791234000.250,
  "uid": "C9xKz13aR8b3xQ1",
  "id.orig_h": "10.0.2.15",
  "id.orig_p": 52344,
  "id.resp_h": "192.168.100.1",
  "id.resp_p": 53,
  "proto": "udp",
  "query": "example.com",
  "qtype_name": "A",
  "rcode_name": "NOERROR",
  "answers": [
    "104.20.23.154",
    "172.66.147.243"
  ],
  "rtt": 0.0125
}
```

### Field-by-Field Breakdown

| Field Name | Technical Definition | SOC Analytical Value |
| :--- | :--- | :--- |
| **`ts`** | Unix Epoch timestamp when query packet was observed. | Correlates DNS requests with subsequent outbound web or TLS connections. |
| **`uid`** | Globally unique 18-character session identifier. | **Forensic Pivot:** Correlates `dns.log` directly back to `conn.log` and `ssl.log`. |
| **`id.orig_h`** | Originating client IP address. | Identifies internal host issuing the DNS lookup request. |
| **`id.resp_h`** | Responding DNS resolver IP address. | Detects unauthorized external DNS resolvers bypassing corporate policy. |
| **`query`** | Requested domain name string. | Highlights target domains (e.g., `example.com`, `malicious-c2.net`). |
| **`qtype_name`** | Human-readable record type requested. | Identifies request intent (`A`=IPv4, `AAAA`=IPv6, `TXT`=Text/Tunneling, `PTR`=Reverse). |
| **`rcode_name`** | Response status code returned by server. | Flags success (`NOERROR`), non-existent domains (`NXDOMAIN`), or errors (`SERVFAIL`). |
| **`answers`** | Array of returned record values or IP addresses. | Uncovers infrastructure IP aliases used by threat actors behind dynamic DNS. |
| **`rtt`** | Round-trip latency in seconds. | Measures delay between query transmission and server response. |

## 3. Threat Hunting & Anomaly Patterns in `dns.log`

SOC analysts and threat hunters inspect `dns.log` datasets to isolate four primary anomaly vectors:

### A. High-Volume `NXDOMAIN` Spikes (Domain Generation Algorithms - DGA)
* **Observed Pattern:** A single internal host receives hundreds of `rcode_name: "NXDOMAIN"` responses within a short time window targeting pseudo-random domain strings (e.g., `a7x9q2p.biz`, `z8m3k1w.info`).
* **Technical Threat:** Malware utilizing DGAs to contact dynamic C2 servers before the domain has been registered by the attacker.

### B. Encoded Query Strings & `TXT` Record Anomalies (DNS Tunneling)
* **Observed Pattern:** An endpoint transmits unusually long, base64-encoded subdomains (e.g., `aGVsbG8td29ybGQ1Njc4OTA.tunnel.attacker.com`) requesting `TXT` or `NULL` record types.
* **Technical Threat:** **DNS Tunneling / Data Exfiltration**. Adversaries encode sensitive host data inside DNS request payloads to bypass perimeter firewalls that allow unrestricted outbound UDP port 53 traffic.

### C. Rare / Long-Tail Domain Access
* **Observed Pattern:** Aggregating DNS queries across an enterprise reveals a domain requested by only 1 host out of 10,000 workstations.
* **Technical Threat:** Low-and-slow C2 channels or targeted phishing payload downloads.

### D. Unsanctioned Outbound Resolvers
* **Observed Pattern:** Workstations sending queries (`id.resp_h`) directly to external public resolvers (`8.8.8.8`, `1.1.1.1`) rather than approved internal corporate DNS resolvers.
* **Technical Threat:** Perimeter security policy violations or malware attempting to bypass internal DNS logging and filtering controls.

## 4. Key SOC Investigative Questions

When evaluating suspicious DNS activity in `dns.log`, systematic analysts answer these core questions:

1. **Which specific device generated the request (`id.orig_h`)?**
2. **What exact domain string was queried (`query`)?**
3. **What record type was requested (`qtype_name`)?**
4. **Which resolver handled the query (`id.resp_h`)?**
5. **Did the resolver respond, and what code was returned (`rcode_name`)?**
6. **Which IP addresses were returned in the resolution (`answers`)?**
7. **Did a corresponding outbound TCP session immediately follow in `conn.log` using the same `uid`?**

## 5. Key Portfolio Takeaways

* **`dns.log` provides human-readable context for network connections that IP addresses alone cannot supply.**
* **The connection `uid` connects `dns.log` directly to transport layer flows in `conn.log`.**
* **Not all `NXDOMAIN` responses indicate malware:** Misconfigured network applications and mistyped web URLs trigger benign `NXDOMAIN` errors daily; baseline host history before escalating.
