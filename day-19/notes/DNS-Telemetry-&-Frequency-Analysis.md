# Technical Note: DNS Telemetry & Frequency Analysis with Zeek

**Author:** Serah Mulwa

**Module:** Day 19 - Network Threat Hunting with Zeek

## 1. Executive Summary

The Domain Name System (DNS) is often called the backbone of network communication—and the primary communication channel for network adversaries. Malware command-and-control (C2) agents, data exfiltration scripts, and phishing links almost always begin with a DNS lookup.

This technical note documents the forensic analysis of `dns.log` generated by Zeek 9.0.1 from controlled network traffic (`day19.pcap`). It details field extraction techniques using `jq`, frequency counting pipelines, response code interpretation (`rcode_name`), and threat-hunting methodologies for identifying suspicious DNS patterns.

## 2. Command-Line Extraction & TSV Formatting

To parse raw JSON DNS telemetry (`LogAscii::use_json=T`) into a clean, human-readable Tab-Separated Value (TSV) format for rapid investigation, we executed the following `jq` query:

```bash
jq -r '
[
  .query,
  .qtype_name,
  .rcode_name,
  ."id.orig_h",
  ."id.resp_h"
] | @tsv
' output/zeek/dns.log
```

### Extracted Field Definitions:

* **`.query`:** The exact domain name requested by the client (e.g., `example.com`).
* **`.qtype_name`:** The DNS record type requested (`A` for IPv4 host address, `AAAA` for IPv6 host address).
* **`.rcode_name`:** The response status code returned by the DNS resolver (`NOERROR`, `NXDOMAIN`, `SERVFAIL`).
* **`."id.orig_h"`:** The internal originating endpoint IP (`10.0.2.15`).
* **`."id.resp_h"`:** The destination DNS resolver IP (`192.168.100.1`).

## 3. Frequency Analysis — Identifying High vs. Low Count Domains

Threat hunters utilize frequency counting to separate high-volume baseline background traffic from low-volume "long-tail" queries that may indicate targeted attack activity.

### Frequency Counting Pipeline:

```bash
jq -r '.query // empty' output/zeek/dns.log | sort | uniq -c | sort -nr
```

### Observed Lab Query Distribution:

```text
      4 example.com
```

* **Analytical Insight:** `uniq -c` counts total **log records**, not necessarily unique users or distinct TCP sessions. Multiple queries for `example.com` occurred because modern OS network stacks request both IPv4 (`A`) and IPv6 (`AAAA`) addresses simultaneously.

## 4. Investigating DNS Failures (`rcode_name != NOERROR`)

Spikes in unsuccessful DNS responses can indicate automated malware cycling through dead Command & Control (C2) infrastructure or dynamic Domain Generation Algorithms (DGA).

### Failure Isolation Query:

```bash
jq -c '
select(
  has("rcode_name") and
  .rcode_name != "NOERROR"
)
' output/zeek/dns.log
```

### Key RCODE Interpretations:

* **`NOERROR` (Code 0):** Query completed successfully; valid answer returned.
* **`NXDOMAIN` (Code 3):** Non-Existent Domain. The domain name queried does not exist in the DNS hierarchy. High volumes indicate DGA activity or dead C2 infrastructure.
* **`SERVFAIL` (Code 2):** Name server failed to process the query due to server-side errors or DNSSEC validation failures.
* **`REFUSED` (Code 5):** Name server refused to process the query due to policy or access control restrictions.

> **Analyst Caution:** Never assume a failed DNS lookup is automatically malicious. User typos, expired domains, and network misconfigurations routinely generate benign `NXDOMAIN` responses.

## 5. Key Portfolio Takeaways

* **DNS telemetry reveals intent:** Analyzing requested domains provides clear insight into host behavior prior to connection establishment.
* **Frequency analysis isolates anomalies:** High-frequency queries represent standard background noise, whereas rare, low-frequency queries deserve close investigation.
* **Contextualize failure codes:** Always correlate `NXDOMAIN` spikes with connection states (`conn.log`) and endpoint indicators before drawing conclusions.
