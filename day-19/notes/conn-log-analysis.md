# Technical Note: Zeek Connection Analysis & conn.log Mechanics

**Author:** Serah Mulwa

**Module:** Day 19 - Network Threat Hunting with Zeek

## 1. Executive Summary

In Network Security Monitoring (NSM), **`conn.log`** serves as Zeek's foundational ledger. It captures fundamental session telemetry for every observed TCP, UDP, and ICMP network flow across an interface or packet capture file.

Instead of requiring analysts to manually reconstruct raw TCP streams in Wireshark, `conn.log` aggregates bi-directional packet metadata into structured records detailing *who* communicated with *whom*, *when*, *for how long*, *using which protocol*, and *how much data was exchanged*. This technical note explores `conn.log` field structures, connection state codes, and practical SOC analysis workflows.

## 2. Anatomy of a Zeek Connection Record

Below is an example of a JSON-formatted connection log record generated by Zeek:

```json
{
  "ts": 1791234000.125,
  "uid": "C9xKz13aR8b3xQ1",
  "id.orig_h": "10.0.2.15",
  "id.orig_p": 52344,
  "id.resp_h": "192.168.100.1",
  "id.resp_p": 53,
  "proto": "udp",
  "service": "dns",
  "duration": 0.015,
  "orig_bytes": 52,
  "resp_bytes": 100,
  "conn_state": "SF",
  "orig_pkts": 1,
  "resp_pkts": 1
}
```

### Field-by-Field Breakdown

| Field Name | Technical Definition | SOC Investigation Value |
| :--- | :--- | :--- |
| **`ts`** | Unix Epoch timestamp when session began. | Establishes exact chronological timeline across security sensors. |
| **`uid`** | Globally unique 18-character session string. | **Forensic Pivot:** Connects `conn.log` to `dns.log`, `ssl.log`, and `http.log`. |
| **`id.orig_h`** | Originator IP address (session initiator). | Identifies local endpoint or client requesting service. |
| **`id.orig_p`** | Ephemeral port used by originator. | Differentiates simultaneous connections originating from the same host. |
| **`id.resp_h`** | Responder IP address (session target). | Identifies destination server or upstream service. |
| **`id.resp_p`** | Destination port on responder. | Reveals target service port (e.g., 53 for DNS, 443 for HTTPS). |
| **`proto`** | Transport protocol (`tcp`, `udp`, `icmp`). | Determines lower-level transport mechanics. |
| **`service`** | Application protocol detected by DPD. | Identifies actual protocol running over socket (e.g., `ssl`, `dns`, `http`). |
| **`duration`** | Active session lifetime in seconds. | High values (`>3600s`) can indicate persistent C2 beaconing. |
| **`orig_bytes`** | Payload bytes sent by originator. | High outbound payload (`orig_bytes >> resp_bytes`) signals data exfiltration. |
| **`resp_bytes`** | Payload bytes sent by responder. | High inbound payload signals large downloads or file transfers. |
| **`conn_state`** | Abbreviated connection lifecycle summary. | Identifies successful connections, dropped packets, or port scans. |
| **`orig_pkts`** | Packet count sent by originator. | Evaluates traffic volume and burst patterns. |
| **`resp_pkts`** | Packet count sent by responder. | Evaluates server responsiveness and throughput. |

> **Originator vs. Responder Rule:** Do not automatically equate `orig` with "Internal Workstation" or `resp` with "External Server". Originator strictly refers to whichever host transmitted the initial packet of a session.

## 3. Interpreting Zeek Connection States (`conn_state`)

Zeek categorizes connection outcomes into standardized two-letter state codes:

| State | Primary Interpretation | Technical Description & Threat Hunting Context |
| :--- | :--- | :--- |
| **`SF`** | Normal establishment & completion. | Full 3-way TCP handshake completed and closed gracefully via FIN/ACK exchange. Represents normal, healthy session traffic. |
| **`S0`** | Attempted connection, no response. | Originator sent a TCP SYN, but no reply (SYN-ACK or RST) was received. Spikes in `S0` from a single host indicate dead destinations, firewall blocks, or active network reconnaissance. |
| **`REJ`** | Connection rejected. | Responder actively rejected the session by replying with a TCP RST packet. A sudden flood of `REJ` states indicates active port scanning against listening hosts. |
| **`S1`** | Established, incomplete teardown. | Connection handshake succeeded, but the capture terminated before a formal teardown was observed (common in truncated PCAPs). |
| **`RSTO`** | Originator reset connection. | Session was forcibly terminated by the originator sending a TCP RST packet. |
| **`RSTR`** | Responder reset connection. | Session was forcibly terminated by the responder sending a TCP RST packet (often seen when security devices sever unauthorized connections). |

## 4. SOC & Job Market Application

* **Data Exfiltration Triage:** Analysts compare `orig_bytes` to `resp_bytes`. If an internal host transfers gigabytes of data (`orig_bytes`) to an external IP while receiving minimal bytes back (`resp_bytes`), this imbalance triggers an exfiltration investigation.

* **Reconnaissance & Scan Detection:** Analysts query `conn.log` for high counts of `S0` or `REJ` states originating from a single internal host toward multiple internal destinations, flagging lateral port sweeps.

* **Beaconing Analysis:** Threat hunters calculate statistical variances in connection `duration` and interval gaps (`ts`) to discover automated malware command-and-control (C2) heartbeat callbacks.

## 5. Key Takeaways

* **`conn.log` provides top-level network session visibility without needing raw PCAP files.**

* **The connection `uid` is the single most important correlation field across Zeek logs.**

* **Byte count ratios (`orig_bytes` vs `resp_bytes`) expose abnormal traffic directionality and data staging.**
